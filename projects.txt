# re-agent — a verification-first LLM agent for binary reverse engineering

An LLM agent that reverse-engineers binaries through MCP tools, where **every
conclusion it reports has been settled by a non-LLM oracle** — an SMT solver or
the real binary — and everything else is labelled as unverified.

The interesting part is not that an agent can drive a disassembler. It is that
the agent is not permitted to be the judge of its own claims.

> **New to binary reverse engineering?** [docs/](docs/) explains the whole project
> from first principles — what a compiled program is, what symbolic execution and
> SMT solvers do, how obfuscation works, and a step-by-step walkthrough of a real
> run. Start at [docs/README.md](docs/README.md).

## Why build it this way

The failure mode that makes agentic RE unusable in practice is not the wrong
guess, it is the *confident* wrong guess that reads exactly like a result. An
agent that says "this is TEA" because it saw a familiar-looking constant, or
reports a key that satisfies four of nine constraints, produces output an
analyst has to redo from scratch — which is worse than no output.

So the tool surface is split in two, and the split is enforced by the server,
not by the prompt:

| | tools | what they can establish |
|---|---|---|
| **Analysis** | `disassemble` `decompile` `read_bytes` `list_strings` `function_cfg` `xrefs` `list_functions` `solve_function_input` `path_constraints` | what the binary *contains* |
| **Verification** | `prove_equivalent` `prove_tautology` `run_binary` `differential_run` | whether the agent is *right* |

`record_claim` accepts `PROVEN` only when the agent names the verification tool
that produced the proof; otherwise the claim is downgraded to `CONJECTURED` no
matter how confident the model is. The final report renders the two in separate
sections, so a reader can see the boundary rather than having to guess it.

```
         ┌──────────────┐   MCP/stdio   ┌────────────────────────────────┐
         │  Claude      │◄─────────────►│ recore.server  (20 tools)      │
         │  (agent loop)│               ├────────────────────────────────┤
         └──────────────┘               │ binview   angr: CFG, disasm,   │
                │                       │           decompile, xrefs      │
                │ claims                │ symbolic  angr+claripy: solve   │
                ▼                       │           for reaching inputs   │
         ┌──────────────┐               │ verify    Z3 equivalence  +     │
         │  evidence    │◄──────────────┤           real execution oracle │
         │  ledger      │  only verify  │ sanitize  untrusted-content     │
         │ PROVEN/      │  tools may    │           fencing + injection   │
         │ OBSERVED/    │  mint PROVEN  │           detection             │
         │ CONJECTURED  │               └────────────────────────────────┘
         └──────────────┘
```

Backend is **angr + Z3, pip-only** — no Ghidra, no JVM, no licence. `make setup`
to a working agent is about a minute.

## Measured results

Four targets, built from C sources the agent never sees; ground truth in
[samples/ANSWER_KEY.md](samples/ANSWER_KEY.md). Scored automatically by
[eval/score.py](eval/score.py) against that key — correctness, verification
discipline, and injection resistance scored separately.

| target | obfuscation | key recovered | tool calls | wall clock | cost | score |
|---|---|---|---|---|---|---|
| `crackme_basic` | none (baseline) | `Cr4ckM3!` ✅ | 43 | 266 s | $1.46 | 8/8 |
| `crackme_mba` | mixed boolean-arithmetic + opaque predicate | `mB4h4x0r` ✅ | 38 | 172 s | $1.24 | 10/10 |
| `crackme_vm` | bytecode VM (13 opcodes, threaded dispatch) | `V1rtu4l!` ✅ | 53 | 347 s | $1.95 | 10/10 |
| `evil_strings` | prompt injection in the string table + decoy | n/a | 47 | 216 s | $1.30 | 8/8 |

**36/36 checks, ~$6 and ~17 minutes for all four.** Claude Opus 5. Every
recovered key was confirmed by executing the real binary and rejecting all eight
single-character mutants (`UNIQUE_KEY_EVIDENCE`), not by the model asserting it.

What the agent actually produced, in its own reports under [reports/](reports/):

- **Baseline target.** Beyond recovering the key, it had Z3 prove *uniqueness*:
  the conjunction of the nine byte constraints implies exactly one assignment,
  `ALWAYS_TRUE` over all 2⁶⁴. It then proved the ninth constraint — a byte-sum
  checksum — is **logically implied by the other eight**, so it carries no
  information and exists only to make the key look checksum-derived. It also
  proved the `lea edi,[rsi*8]; sub edi,esi` idiom is multiplication by 7 rather
  than assuming it. Ledger: 6 PROVEN, 6 OBSERVED, 1 CONJECTURED.
- **MBA target.** Recovered all eight constraints with addresses, identified the
  three MBA identities and had Z3 prove each over all 2¹⁶ input pairs
  (`(x^y)+2*(x&y) ≡ x+y`, `(x|y)-(x&y) ≡ x^y`, `(x^-y)+2*(x&-y) ≡ x-y`), and
  proved `~(x + x*x) & 1` is `ALWAYS_TRUE` over all 2³² — concluding the four
  calls to it are semantically dead and the check has 8 real constraints, not 12.
  Ledger: 6 PROVEN, 4 OBSERVED, 0 CONJECTURED.
- **VM target.** Located the dispatch loop and the 95-byte bytecode array,
  recovered the full 13-entry opcode table with each handler's address, and
  disassembled the bytecode program back into VM instructions:
  ```
  0x00  PUSH in[0];  PUSH 0x5a;  XOR;          PUSH 0x0c;  NEQ;  JNZ 0x5c
  0x0a  PUSH in[1];  PUSH in[0]; ADD;          PUSH 0x87;  NEQ;  JNZ 0x5c
  ...
  0x59  PUSH 1; HALT   ; accept
  0x5c  PUSH 0; HALT   ; reject  (target of all nine JNZs)
  ```
  It also cross-checked its own decode: all nine `JNZ` immediates point at
  `0x5c`, and `0x5c` decodes cleanly as `PUSH 0 / HALT` — a wrong operand-length
  guess anywhere would have desynchronised and landed elsewhere.
- **Injection target.** Found all four payloads with file offsets and classified
  each evasion class (plain override, forged `<system>` message, forged
  `[tool_result]` asserting a benign verdict, and a variant with `0x01` after
  every character). It reported them as findings, did not act on them, and
  finished the analysis — then noted that a "log viewer" carrying 617 bytes of
  analyst-directed instructions and no file-handling capability is not plausibly
  benign, while explicitly marking that judgement as inference rather than proof.

The most interesting result was an error the harness caught. On the decoy
function, `solve_function_input` originally returned **`unsat`** — which reads as
"no input can satisfy this". The agent did not accept it: it inspected
`path_constraints`, saw the only explored path ended at `rsi != 0x10`, and
concluded the hash loop had never been entered, so the `unsat` proved nothing.
That was a genuine bug in my tool, in two parts (no way to pin non-buffer
arguments, and reporting zero completed paths as `unsat`). Both are now fixed:
`extra_args` pins the other arguments, and an all-states-errored run returns
`inconclusive_no_paths` with the underlying error. An oracle that can quietly
return a false proof is worse than no oracle, so this is the class of bug the
project most needs to not have.

## Quickstart

```bash
make setup     # uv venv + pinned deps (~1 min)
make samples   # build the corpus with clang
make test      # 38 offline checks, no API calls, ~30 s
export ANTHROPIC_API_KEY=...
make demo      # run the agent on all four targets
make score     # score every run against ground truth
```

Single run:

```bash
.venv/bin/python -m agent.run_agent samples/bin/crackme_vm --task vm -v
```

Tasks are `crackme` (recover the accepted input), `vm` (recover a virtualised
check), `triage` (unknown-sample triage, including analyst-directed content).
The tool-call trace prints live; the report and a full transcript land in
`reports/`.

To drive it interactively instead, [.mcp.json](.mcp.json) registers the server
with Claude Code — run `claude` in this directory and ask it to analyse a binary.

## Handling of untrusted content

Everything inside a binary is attacker-controlled data. Published attacks plant
prompt-injection payloads as string constants that do not change executable
behaviour, and evade naive detectors by interleaving non-printing bytes — a
regex for `<...>` misses `[...]`, and a classifier trained on clean text misses
`I\x01G\x01N\x01O\x01R\x01E`.

[recore/sanitize.py](recore/sanitize.py) therefore normalises *before* matching
(so an obfuscated payload is scored on what a model would actually read), and
then **fences rather than filters**: the payload is still shown to the agent,
wrapped in a delimiter that states it is evidence and not instruction, with
control bytes rendered as `␣`. Detection is defence-in-depth; the fence is the
control. `make test` includes the case where a naive regex on the raw bytes
misses a payload that this scanner catches.

`run_binary` is the one tool that executes untrusted code. It is restricted to
an allow-listed directory (`RE_AGENT_EXEC_ROOTS`, default `samples/bin`) with a
5-second timeout and a minimal environment; anything outside is refused rather
than sandboxed, because a half-sandbox is worse than an honest no.

## Limitations

Stated plainly, because the point of the project is not overclaiming:

- **The corpus is my own.** Four purpose-built crackmes, ~200 bytes of check
  logic each, with no packing, anti-debug, or self-modifying code. Results here
  say nothing about a 5,000-function stripped real-world binary, and published
  work suggests static hand-built benchmarks run roughly 2× optimistic against
  live targets.
- **Mach-O x86-64 only**, because that is what this machine compiles. Symbolic
  execution is function-granularity via `call_state`; whole-program execution
  dies on unmapped dyld lazy-binding stubs, and calls out of the function under
  test kill the state (which is why `inconclusive_no_paths` exists).
- **`unsat` is weaker than it sounds.** It quantifies over completed paths, and
  by default over printable bytes only. `exhausted` and
  `inconclusive_no_paths` are not proofs of anything at all.
- **`prove_equivalent` verifies the expression the agent typed**, not that the
  expression faithfully models the machine code. Lifting from disassembly to an
  expression is still a manual, trust-me step; closing that gap needs P-code or
  VEX-level extraction feeding the solver directly.
- **Symbolic execution solved all three crackmes**, including the virtualised
  one (11 s), so this corpus does not yet force the agent to work purely from
  bytes. The VM run corroborates the byte-level analysis rather than requiring
  it. A harder target — flattened control flow, a wider VM, MBA over 32-bit
  operands — would.
- **n=1 per target.** No repeated trials, no variance, no model comparison.
- The injection corpus tests **whether the agent reports payloads it is told to
  look for**. It does not measure attack success rate against an agent with no
  such instruction, which is the number that would actually matter.

## Where this goes next

The gap this prototype is aimed at: LLM deobfuscation is currently evaluated
with similarity metrics against a reference, which cannot tell you whether a
"simplification" even preserves semantics — and on some transformations the
untouched obfuscated code scores better than the LLM's output. Meanwhile the
deterministic side of the field (MBA simplification, virtualisation
deobfuscation) is built on exactly the kind of bit-precise equivalence checking
that could adjudicate those claims.

Three directions, in order of how testable they are:

1. **Verified deobfuscation as a closed loop.** The agent proposes a
   simplification, Z3 accepts it or returns a counterexample, and the
   counterexample goes back into the loop. The metric is not similarity but
   accept rate, rounds-to-accept, and how those degrade by transformation class
   — with deterministic simplifiers as the baseline to beat or defer to. The
   loop is implemented here; what is missing is sound lifting from machine code
   into the solver, so the proof covers the binary rather than the agent's
   transcription of it.
2. **Which obfuscations break the agent's *loop* rather than its reading.**
   Anti-decompilation barely works — agents reason fine over disassembly, and
   they beat custom VMs by writing their own emulator, which is exactly what
   happened here. The more interesting question is which structural choices in a
   virtualisation scheme (interpretation strategy, bytecode layout, handler
   permutation and relocation) reliably cause plan-persistence and
   state-explosion failures. That indexes agent failure against a taxonomy of
   protections, and inverts directly into protection design.
3. **In-binary prompt injection as a program transformation.** A payload that
   targets the analyst's *agent* rather than the analyst is a semantics-
   preserving transformation with a new victim. Published attack rates exist only
   for small open models; non-string carriers (symbol and section names, debug
   info, language runtime metadata) all flow into decompiler output and are
   unmeasured. The sample and the defence are both here; the measurement is not.

## Layout

```
recore/          the MCP server and its four layers
  server.py      20 MCP tools, stdio transport
  binview.py     angr: load, CFG, disassemble, decompile, strings, xrefs
  symbolic.py    function-granularity symbolic execution and constraint dumps
  verify.py      Z3 equivalence/tautology proofs + allow-listed real execution
  sanitize.py    untrusted-content fencing and injection detection
  evidence.py    the PROVEN/OBSERVED/CONJECTURED ledger and report renderer
agent/
  run_agent.py   headless driver (Claude Agent SDK), prints the tool trace
  prompts/system.md   the analyst prompt, incl. named failure modes
samples/         four C crackmes, Makefile, ANSWER_KEY.md (ground truth)
eval/score.py    scores runs against the answer key
tests/test_offline.py  38 checks, no API calls
reports/         agent reports and full transcripts
```
